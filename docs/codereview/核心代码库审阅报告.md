## 一、agent 模块

### 1.1 Critical — stream () 参数顺序颠倒——已修复

- **问题类型**：功能 Bug
- **涉及文件**：`agent/agent.py` L185、L527
- **问题详情**：
  内部方法 `_stream_iterator` 形参顺序为 `(session_id, version)`，但对外 `stream` 方法传入顺序颠倒为 `(version, session_id)`，异步方法 `astream` 顺序正确。
  默认 `version="v2"` 时，流执行结束后会将字符串 `"v2"` 作为会话 key 调用写回逻辑，导致 `_append_conversation` 无法匹配到 pending 输入，**静默跳过会话历史持久化**，同时 token 统计、会话压缩等操作也会写入错误的会话上下文。

## 二、llm 模块

### 2.1 Critical — usage_metadata 为 None 时解析崩溃——已修复

- **问题类型**：功能 Bug
- **涉及文件**：`llm/llm_client.py` L506–508、L540–542
- **问题详情**：
  代码通过 `getattr(response, "usage_metadata", {}).get(...)` 读取 token 用量。当响应对象存在 `usage_metadata` 属性但值为 `None` 时，`getattr` 会返回 `None` 而非默认空字典，后续调用 `.get()` 会抛出 `AttributeError`，最终被包装为 `LLMResponseDecodeError`。
  流式响应的分片（chunk）几乎始终为 `usage_metadata=None`，导致 `stream` / `astream` 接口极易直接崩溃。
- **解决方案**：
  使用 `getattr(..., None) or {}`；结构化解析路径从 `raw` 读取 `usage_metadata`。

### 2.2 High — attachments 多模态内容被静默丢弃——已修复

- **问题类型**：功能 Bug / 逻辑缺陷
- **涉及文件**：`llm/llm_client.py` L417–418、`model/input.py`
- **问题详情**：
  `UserInput` 数据结构已定义 `attachments` 字段支持多模态输入，但 `_build_messages` 构建请求消息时仅处理 `text` 文本内容，附件内容无任何告警直接丢失，调用方无法感知多模态输入未生效。
- **解决方案**：
  - `Message.content` 升级为 `str | list[str | dict[str, Any]]`
  - `MessageAdapter.to_human_message`：按 base64 / url 构造多模态 `HumanMessage` content blocks
  - `_build_messages` 对 `UserInput` 走 `to_human_message`
  - `attachment_from_fields` 按 data 推断 `format`（http→url，否则 base64）
  - mime_type 暂写死（image/jpeg、audio/wav、application/pdf），后续统计后再改

### 2.3 High — 内置工具被 bind_tools 覆盖丢失（暂不修改，等遇到实际问题再修改）

- **问题类型**：逻辑缺陷
- **涉及文件**：`llm/llm_client.py` L383–384、L490–491
- **问题详情**：
  客户端初始化时通过 `bind(tools=builtin_tools)` 绑定内置工具（如 web search），但后续 Agent 侧调用 `bind_tools(tool_list)` 时，底层实现通常为**替换**而非合并工具列表，导致绑定业务工具后内置工具全部丢失。

### 2.4 Medium — parallel_tool_calls 硬编码开启（暂不修改，等遇到实际问题再修改）

- **问题类型**：设计缺陷
- **涉及文件**：`llm/llm_client.py`
- **问题详情**：
  `parallel_tool_calls=True` 为硬编码配置，部分 LLM Provider 不支持并行工具调用，直接启用会导致请求失败或行为异常，缺少按模型能力动态适配的能力。

### 2.5 Medium — 非文本内容块被静默丢弃——LLM 层已修复（关联 §9.2）

- **问题类型**：逻辑缺陷
- **涉及文件**：`llm/llm_client.py`、`llm/llm_result.py`
- **问题详情**：
  `_normalize_content` 方法仅保留 text 类型内容块，其余类型直接丢弃，极端场景下可能出现消息内容为空但请求标记为「成功」的异常状态（典型如模型 `reasoning` / `thinking` 块）。
- **解决方案**（已落地）：
  1. `LLMResult` 字段对齐 LangChain ContentBlock：`text`（TextContentBlock）+ `reasoning`（ReasoningContentBlock）；第一期仅保留这两类，工具调用仍走独立 `tool_calls`
  2. `_normalize_content` / `_parse_response` / `_parse_structured_response`：优先解析 `AIMessage.content_blocks`，回退原始 `content`；提取 `text` 与 `reasoning`（兼容 `thinking`、OpenAI `summary`）；未知 block 打 warning，不再静默丢弃
- **后续**：LLM 层原料已保留；面向前端的稳定展示契约见 §9.2（`AgentResult` / `AgentEvent`，**核心已落地**），勿将 `LLMResult` 直接当作 UI 契约。注意与 ReAct `state.reasoning`（Action 执行意图）语义不同，不可混用。

### 2.6 Medium — API 密钥明文存储易泄漏（暂不修改）

- **问题类型**：安全风险
- **涉及文件**：`llm/llm_client.py`
- **问题详情**：
  `api_key` 以明文形式存储在 Pydantic 模型中，易在对象序列化、日志打印、异常栈输出时意外泄漏敏感凭证。

### 2.7 Medium — 依赖上下文对象导致层次倒置

- **问题类型**：架构设计
- **涉及文件**：`llm/llm_client.py`
- **问题详情**：
  `LLMClient` 直接依赖 `BaseContext` 实现 skill 注入能力，底层 LLM 模块反向依赖上层运行时上下文，造成模块层次倒置，不利于独立测试与复用。

## 三、strategy 模块

### 3.1 High — 工具执行成功结果不写入 observations——已修复

- **问题类型**：逻辑 Bug
- **涉及文件**：`strategy/react/node/reason_node.py`、`final_node.py`
- **问题详情**：
  1. `_build_input` 仅在本次 LLM 调用输入中临时拼接 observations，未持久化到 state
  2. `_handle_result` 工具执行成功路径不回写 state.observations，仅错误路径会写入，且为**全量替换**而非追加
  3. `FinalNode` 仅读取 `state.observations` 生成最终回复
     多步工具成功执行后，Final 节点的 observations 通道为空或保留过时数据，只能依赖 trajectory 副作用；错误或无工具调用场景还会直接覆盖历史 observations。

### 3.2 High — HITL 无审批响应时绕过校验执行工具——已修复

- **问题类型**：安全 / 逻辑缺陷
- **涉及文件**：`strategy/react/node/action_node.py`（`_handle_tool_calls`）
- **问题详情**：
  当 `hitl_state.response` 为空但 `tool_state.tool_calls` 非空时，逻辑落入 fallback 分支，直接路由到工具执行节点。在 checkpoint 恢复、流程重放等场景下，**处于审批中的工具调用可能绕过人工审批直接执行**。
- **解决方案**：
  - 无 HITL `response`（及有 `response` 但无法匹配合法 `request` 类型）时不再进 tool，改为 `task_status=failed`
  - 清空 `tool_state` / `hitl_state`，递增 `step_count`，不写 tool_call trajectory
  - 路由：`failed` → reason → final（与 `cancelled` 收敛路径一致）

### 3.3 High — HITL 补参后强制清空缺参列表，无二次校验——已修复

- **问题类型**：安全 / 逻辑缺陷
- **涉及文件**：`strategy/react/node/action_node.py`（`_fill_tool_calls` / INPUT 恢复分支）
- **问题详情**：
  人工恢复（resume）流程后，无论缺失参数是否实际补齐，代码一律强制 `missing_args = []`，且不再执行 `_get_missing_parameters` 二次校验。参数不完整的工具调用可直接进入审批或执行环节，存在运行时异常风险。
- **解决方案**：
  - `_fill_tool_calls` 仅按 resume `values` 填充参数，**不再**无条件清空 `missing_args`
  - INPUT 恢复后强制 `_get_missing_parameters` 二次校验；仍缺参则再次 `_handle_missing_parameters`（再 interrupt）
  - 校验通过后再 `_mark_missing_parameters(..., {})` 清空标记，随后才进入审批或执行

### 3.4 High — 工具列表构图时快照，与运行时注册表不一致——核心已修复

- **问题类型**：设计 / 逻辑缺陷
- **涉及文件**：`react_strategy.py`（`build`）、`action_node.py`、`tool/tool_registry.py`
- **问题详情**（历史）：
  `ReActStrategy.build()` 曾通过 `registry.list_definitions()` **快照**工具列表并注入 `ActionNode(tool_list=...)`；`ToolExecutor` / `ToolNode` 则持有同一 `ToolRegistry` 的**活引用**。构图后再 `register`（典型：`Agent.register_mcp_tools()`）会导致选型与执行契约错位；Action 侧还曾用 `fetch`/`filesystem` 服务名 always-expose（关联 §11.1）。
- **解决方案**（核心已落地）：
  1. `ActionNode` 持有活 `ToolRegistry`；可见集 / 验参 / 审批均经 `list_definitions()` / `get()` / `default_tools()`，不再冻结 `_tool_list`
  2. `default_tools` 下沉至 `ToolRegistry`，仅 Skill meta（`load_skill` / `read_skill_resource`），**不再** always-expose MCP
  3. `_available_tools` 仍留在 Action（依赖 Skill 上下文裁剪）
- **后续**：
  - 单测补齐：构图后注册 → Action 可见（`test_action_tools_follow_skill_metadata` 已含 late register 断言）
  - §11.1 其余 MCP 可信标记改造仍独立跟踪

### 3.5 High — PlanExecuteStrategy 为空实现仍注册到工厂（暂不处理，CR之后会实现）

- **问题类型**：设计 / Bug
- **涉及文件**：`plan_execute/plan_execute_strategy.py`、`strategy_factory.py`
- **问题详情**：
  `PlanExecuteStrategy` 的 `build` / `as_node` / `as_subgraph` 方法全部为空实现（`pass`），但 StrategyFactory 仍按 ReAct 风格的参数构造该对象。调用方使用时极易触发 `TypeError` 或拿到无效的 `None` 返回值，且无任何告警。

### 3.6 Medium — retry_count 计数语义混用——已修复

- **问题类型**：设计缺陷
- **涉及文件**：`strategy/react/node/`、`strategy/react/schema.py`
- **问题详情**（历史）：
  `retry_count` 同时统计「无工具可调用 / 工具名非法」的输入错误与「工具执行失败」的运行时错误，两种场景重试策略与根因不同，混用会导致错误场景过度重试或真实失败重试不足。
- **解决方案**（已落地）：
  1. `retry_count` 语义收敛为仅统计选型异常（`no_tool_calls` / `invalid_tools`），由 Action 递增
  2. `step_count` 改由 Reason 独占递增与上限判定；选型失败不消耗 step
  3. 工具执行失败不再计入 `retry_count`，改走 observation + 步数预算（失败信息供后续推理，而非机械重试）
- **后续**：需对工具执行失败场景进行相关测试

### 3.7 Medium — 无工具场景 prompt 与 schema 约定不一致——已修复

### 3.9 High — 无 Skill 时动态工具暴露退化为仅 meta 工具——核心已修复

- **问题类型**：逻辑缺陷 / 可用性
- **涉及文件**：`strategy/react/node/action_node.py`（`_available_tools` / `_default_tools`）
- **关联**：§5.1（`allowed_tools` 语义）、§3.4（工具列表快照）
- **问题详情**（历史）：
  Action 对模型可见的工具集由 `_available_tools` 按 Skill 状态裁剪。裁剪落地初期在 `loaded_skills` 为空时直接返回 `_default_tools()`（仅 meta + 常驻 MCP），**未区分**「未配置 Skill」与「已配置但未 load」两种空态，导致无 Skill 场景下业务工具对模型不可见。
- **解决方案**（核心已落地）：
  1. `not context.skill_list` → 返回全量 `_tool_list`
  2. `skill_list` 非空且 `not loaded_skills` → 仍返回 `default_tools`（渐进披露）
  3. 已 load 后的 `allowed_tools` 白名单 / `None` 全量兼容逻辑保持不变
- **后续**：
  - 已 load 且白名单与注册表无交集：宜告警 / 可观测，勿静默回退全量
  - 补单测：无 Skill + 业务工具；有 Skill 未 load 时仅 meta
  - 仍受 §3.4 快照限制：后注册工具即使 registry 已更新，Action 可见集也可能落后

### 3.10 High — ReAct 本轮上下文组装缺少轮次边界（优化点）——已修复

- **问题类型**：架构设计 / 逻辑缺陷
- **涉及文件**：`strategy/react/node/reason_node.py`、`action_node.py`、`final_node.py`、`react_strategy.py`（`to_strategy_input`）
- **关联**：§3.1（observations 与 trajectory 副作用）、§3.7（无工具场景 status 约定）
- **问题详情**：

  1. 跨轮 `conversation` 仅在整轮结束后由 Agent `_append_conversation` 写入；本轮用户文本只进入 `task`，不进入聊天消息序列。
  2. Reason / Action / Final 各自 `_build_history = conversation + trajectory`，工具轨迹直接拼在上一轮 assistant 之后，缺少「本轮 USER」锚点。
  3. 多步工具后（step≥1）模型易把上一轮用户话当作当前目标（例如先「你好」再执行任务时，误判为问候并 `completed`）。
  4. `trajectory` 同时出现在 history 与 `_build_input` JSON，双写且序列化质量差；节点间组装逻辑易漂移。
     在节点内临时插入 `Message(USER, task)` 可缓解，但未统一入口与不变量，属于局部补丁。
- **优化建议**：

  1. 引入统一的 ReAct 消息组装（Chat 平面）：`prior conversation + current_user + turn trajectory`，三节点共用，禁止各自拼装。
  2. 在策略入场（`to_strategy_input` / state 初始化）固定本轮 USER 锚点；`trajectory` 仅追加本轮 tool_call / tool_result / final。
  3. Control 平面（`task` / `observations` / `reasoning`）与 Chat 平面分离；`user_input` 不再重复塞 `trajectory`。
  4. 补单测：多轮「问候 → 执行任务」在 load_skill 后仍保持本轮任务目标；断言消息序不变量。

## 四、graph 模块

### 4.1 Medium — 异步注册不完整，标记错误直接失败——已修复

- **问题类型**：逻辑 / 设计缺陷
- **涉及文件**：`graph/graph.py`、`graph/node/node.py`
- **问题详情**：
  `is_async` 标记仅注册 `run` 或 `arun` 其中一个实现，若标记与实际实现不匹配，调用会直接硬失败，缺少兼容降级与校验提示。
- **解决方案**：
  1. 取消 `is_async` 二选一注册；`Graph.build` 通过 `RunnableCallable(func=node.run, afunc=node.arun)` 同时挂上同步 / 异步路径
  2. `Node` 将 `run` / `arun` 均标为 `@abstractmethod`，强制子类双实现，从类型层消除标记与实现不一致

### 4.2 Medium — 编译依赖运行时配置，职责倒置

- **问题类型**：架构设计
- **涉及文件**：`graph/root_graph.py`
- **问题详情**：
  `RootGraph.compile` 直接依赖 `RuntimeConfig`，图结构定义层反向依赖运行时层，模块职责倒置，不利于图结构的独立测试与复用。

### 4.3 Medium — 子图转节点方法重复且重复编译

- **问题类型**：设计缺陷
- **涉及文件**：`graph/subgraph.py`

### 4.4 Medium — 重名静默覆盖，无边拓扑校验

- **问题类型**：逻辑缺陷
- **涉及文件**：`graph/`
- **问题详情**：
  注册同名节点或子图时静默覆盖旧定义，无冲突告警；边注册时不做拓扑校验，可能出现无效边、循环依赖等运行时才暴露的问题。

### 4.5 Low — 抽象类无抽象方法，常量映射为死代码

## 五、model 模块

### 5.1 Medium — 工具白名单语义模糊——已修复

- **问题类型**：逻辑 / 安全风险
- **涉及文件**：`model/`
- **问题详情**：
  格式非法的 `allowed_tools` 会被转为空列表 `[]`，语义为「禁止所有工具」；而「无限制」语义为 `None`。两者行为差异巨大且无明确校验提示，配置错误易导致非预期的权限收缩。
- **解决方案**：
  保留 None = 未配置 / 不限制；遇到非法类型时抛出警告，不要静默 []；合法空列表 [] 才是「禁止额外业务工具」。
- 📌**关于 skill 工具发现可能还需进一步设计**（无 Skill / 未 load / 白名单无效关联的暴露策略见 §3.9）

### 5.2 Low — 数据结构一致性不足——已修复

- **问题类型**：代码规范
- **涉及文件**：`model/`
- **问题详情**：
  - `append_messages` 为不可变操作，`ConversationState.append` 为可变操作，接口语义不一致
  - 枚举类型混用 `str Enum` 与普通 Enum
  - 部分目录缺少 `__init__.py`，包结构不规范
- **解决方案**：

## 八、capability 模块

### 8.1 High — HTTP Skill 全部候选失败触发变量未定义错误

- **问题类型**：功能 Bug
- **涉及文件**：`capability/skill/skill_parser.py` L72–81
- **问题详情**：
  循环解析所有候选 Skill 全部失败时，`content` / `name` 变量未被赋值，后续仍调用 `_parse_frontmatter(content)` 触发 `UnboundLocalError`。现有测试仅断言「抛出任意异常」，掩盖了真实的失败形态。

### 8.2 High — HTTP Skill 包模型残缺，远程目录结构不可感知

- **问题类型**：功能缺失 / 逻辑缺陷（使用与集成中发现）
- **涉及文件**：`capability/skill/skill_parser.py`（`_parse_http`）、`capability/skill/skill_loader.py`、`tool/toolkit/skill.py`（`read_skill_resource` / `_aread_package_resource`）、`model/skill.py`（`SkillPackage`）
- **问题详情**：
  Remote（HTTP）Skill 在集成中实质不可用。配置 URL 仅作为 **base URL**：解析阶段只尝试拼接 `SKILL.md` 等候选文件名并拉取 frontmatter，**不会**像本地 FILE Skill 那样枚举 `scripts/`、`references/`、`assets/` 及附加资源。

因此形成与 FILE 不对等的能力缺口：


| 能力                               | FILE               | HTTP                                    |
| ------------------------------------ | -------------------- | ----------------------------------------- |
| 拉取`SKILL.md` + frontmatter       | 有                 | 有（仅候选文件名）                      |
| 枚举包内资源路径                   | 有（`_get_files`） | 无（字段恒为空列表）                    |
| `load_skill` 向模型告知可用资源    | 有                 | 无（通常仅返回「loaded」）              |
| `read_skill_resource` 读取包内文件 | 有                 | 无（非 FILE 直接`NotImplementedError`） |

根因是建模不一致：HTTP 被当作「单文件指令源」，FILE 才是「可列举的包」。远端没有本地 `rglob`，又缺少清单协议（frontmatter / manifest 声明相对路径）或按相对路径 `join_url(base, path)` 拉取并缓存的实现，模型既无法感知远端文件夹结构，也无法读取资源。即使修复 §8.1 的失败形态，在补齐包模型与资源读取之前，HTTP Skill 仍无法作为一等公民使用。

- **建议方向**：清单驱动（frontmatter 或旁路 manifest 声明资源相对路径）+ HTTP 路径下 `join_url` GET；补齐后再强化 §8.5 的 SSRF / 体积 / 超时约束。

### 8.3 Medium — 激活标识与配置键不一致导致静默失效

- **问题类型**：逻辑缺陷
- **涉及文件**：`capability/`
- **问题详情**：
  `active_skills` 以 frontmatter 中的 name 字段为标识，而外部 API 以 `skill_list` 的 key 为标识，两者不一致时 Skill 会静默处于 idle 状态，调用方无法感知失效。

### 8.4 Medium — 启动时全量解析，单点故障拖垮整体

- **问题类型**：设计缺陷
- **涉及文件**：`capability/`
- **问题详情**：
  Agent 构造时立即解析全部 Skill（含远程 HTTP Skill），单个远程 URL 加载失败就会导致整个 Agent 初始化失败，缺少降级与容错机制。

### 8.5 Medium — 远程 Skill 缺少安全约束

- **问题类型**：安全风险
- **涉及文件**：`capability/`
- **问题详情**：
  远程 HTTP Skill 未配置 SSRF 防护、响应体积限制、超时控制等安全策略，存在内网探测、资源耗尽等风险。补齐 §8.2 的按路径远程读取后，该面将更尖锐。

## 十一、mcp 模块

### 11.1 Critical — 保留名可绕过内置工具权限控制

- **问题类型**：安全 / 契约缺陷
- **涉及文件**：`mcp/mcp_client.py` L46–54；消费方 `strategy/react/node/action_node.py` L26、L53–61

### 11.2 High — 空白目录解析为进程工作目录

- **问题类型**：安全 / 逻辑缺陷

- **问题详情**：

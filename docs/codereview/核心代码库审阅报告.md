**审阅范围**：model、llm、graph、agent、tool、strategy、runtime、capability、mcp、trace
**风险维度**：功能正确性、安全性、架构设计、生命周期管理、测试覆盖
**补充来源**：静态审阅 + 使用 / 集成过程中发现的可用性缺口（见 §7.5、§8.2、§9.2）

| 等级     | 定义                                                                 | 修复优先级             |

## 一、agent 模块

### 1.1 Critical — stream () 参数顺序颠倒——已修复

- **问题类型**：功能 Bug
- **涉及文件**：`agent/agent.py` L185、L527
- **问题详情**：
  内部方法 `_stream_iterator` 形参顺序为 `(session_id, version)`，但对外 `stream` 方法传入顺序颠倒为 `(version, session_id)`，异步方法 `astream` 顺序正确。
  默认 `version="v2"` 时，流执行结束后会将字符串 `"v2"` 作为会话 key 调用写回逻辑，导致 `_append_conversation` 无法匹配到 pending 输入，**静默跳过会话历史持久化**，同时 token 统计、会话压缩等操作也会写入错误的会话上下文。

## 二、llm 模块

### 2.1 Critical — usage_metadata 为 None 时解析崩溃——已修复

- **问题类型**：功能 Bug
- **涉及文件**：`llm/llm_client.py` L506–508、L540–542
- **问题详情**：
  代码通过 `getattr(response, "usage_metadata", {}).get(...)` 读取 token 用量。当响应对象存在 `usage_metadata` 属性但值为 `None` 时，`getattr` 会返回 `None` 而非默认空字典，后续调用 `.get()` 会抛出 `AttributeError`，最终被包装为 `LLMResponseDecodeError`。
  流式响应的分片（chunk）几乎始终为 `usage_metadata=None`，导致 `stream` / `astream` 接口极易直接崩溃。
- **解决方案**：
  使用 `getattr(..., None) or {}`；结构化解析路径从 `raw` 读取 `usage_metadata`。

### 2.2 High — attachments 多模态内容被静默丢弃——已修复（mime 暂写死）

- **问题类型**：功能 Bug / 逻辑缺陷
- **涉及文件**：`llm/llm_client.py`、`model/input.py`、`model/message.py`、`utils/adapter/message_adapter.py`、`adapter/convert.py`
- **问题详情**：
  `UserInput` 数据结构已定义 `attachments` 字段支持多模态输入，但 `_build_messages` 构建请求消息时仅处理 `text` 文本内容，附件内容无任何告警直接丢失，调用方无法感知多模态输入未生效。
- **解决方案**：
  - `Message.content` 升级为 `str | list[str | dict[str, Any]]`
  - `MessageAdapter.to_human_message`：按 base64 / url 构造多模态 `HumanMessage` content blocks
  - `_build_messages` 对 `UserInput` 走 `to_human_message`
  - `attachment_from_fields` 按 data 推断 `format`（http→url，否则 base64）
  - mime_type 暂写死（image/jpeg、audio/wav、application/pdf），后续统计后再改

### 2.3 High — 内置工具被 bind_tools 覆盖丢失（暂不修改，等遇到实际问题再修改）

- **问题类型**：逻辑缺陷
- **涉及文件**：`llm/llm_client.py` L383–384、L490–491
- **问题详情**：
  客户端初始化时通过 `bind(tools=builtin_tools)` 绑定内置工具（如 web search），但后续 Agent 侧调用 `bind_tools(tool_list)` 时，底层实现通常为**替换**而非合并工具列表，导致绑定业务工具后内置工具全部丢失。

### 2.4 Medium — parallel_tool_calls 硬编码开启（暂不修改，等遇到实际问题再修改）

- **问题类型**：设计缺陷
- **涉及文件**：`llm/llm_client.py`
- **问题详情**：
  `parallel_tool_calls=True` 为硬编码配置，部分 LLM Provider 不支持并行工具调用，直接启用会导致请求失败或行为异常，缺少按模型能力动态适配的能力。

### 2.5 Medium — 非文本内容块被静默丢弃——已修复（LLM 层；关联 §9.2）

- **问题类型**：逻辑缺陷
- **涉及文件**：`llm/llm_client.py`、`llm/llm_result.py`
- **问题详情**：
  `_normalize_content` 方法仅保留 text 类型内容块，其余类型直接丢弃，极端场景下可能出现消息内容为空但请求标记为「成功」的异常状态。
- **解决方案**：
  - 共享 `split_ai_content`：`LLMClient` 与 Adapter 同源拆分 text / reasoning
  - `LLMResult` 新增 `reasoning: str`（模型侧 CoT；与 `ReActState.reasoning` 策略摘要不同）
  - Adapter：messages 流上出现含 reasoning block 的 `AIMessage` 时自动发 `AgentEvent(type="reasoning")`（§9.2 最小切片）

### 2.6 Medium — API 密钥明文存储易泄漏（暂不修改）

- **问题类型**：安全风险
- **涉及文件**：`llm/llm_client.py`
- **问题详情**：
  `api_key` 以明文形式存储在 Pydantic 模型中，易在对象序列化、日志打印、异常栈输出时意外泄漏敏感凭证。

### 2.7 Medium — 依赖上下文对象导致层次倒置

- **问题类型**：架构设计
- **涉及文件**：`llm/llm_client.py`
- **问题详情**：
  `LLMClient` 直接依赖 `BaseContext` 实现 skill 注入能力，底层 LLM 模块反向依赖上层运行时上下文，造成模块层次倒置，不利于独立测试与复用。

## 三、strategy 模块

### 3.1 High — 工具执行成功结果不写入 observations

- **问题类型**：逻辑 Bug
- **涉及文件**：`strategy/react/node/reason_node.py`、`final_node.py`
- **问题详情**：

  1. `_build_input` 仅在本次 LLM 调用输入中临时拼接 observations，未持久化到 state
  2. `_handle_result` 工具执行成功路径不回写 state.observations，仅错误路径会写入，且为**全量替换**而非追加
  3. `FinalNode` 仅读取 `state.observations` 生成最终回复
     多步工具成功执行后，Final 节点的 observations 通道为空或保留过时数据，只能依赖 trajectory 副作用；错误或无工具调用场景还会直接覆盖历史 observations。

### 3.2 High — HITL 无审批响应时绕过校验执行工具

- **问题类型**：安全 / 逻辑缺陷
- **涉及文件**：`strategy/react/node/action_node.py` L291–298
- **问题详情**：
  当 `hitl_state.response` 为空但 `tool_state.tool_calls` 非空时，逻辑落入 fallback 分支，直接路由到工具执行节点。在 checkpoint 恢复、流程重放等场景下，**处于审批中的工具调用可能绕过人工审批直接执行**。

### 3.3 High — HITL 补参后强制清空缺参列表，无二次校验

- **问题类型**：安全 / 逻辑缺陷
- **涉及文件**：`strategy/react/node/action_node.py` L568–578
- **问题详情**：
  人工恢复（resume）流程后，无论缺失参数是否实际补齐，代码一律强制 `missing_args = []`，且不再执行 `_get_missing_parameters` 二次校验。参数不完整的工具调用可直接进入审批或执行环节，存在运行时异常风险。

### 3.4 High — 工具列表构图时快照，与运行时注册表不一致

- **问题类型**：设计 / 逻辑缺陷
- **涉及文件**：`react_strategy.py` L44–49（关联 tool 模块）
- **问题详情**：
  `ActionNode` 初始化时通过 `registry.list_definitions()` 快照工具列表并固化到图结构中；而 `ToolExecutor` 持有动态更新的活注册表。构图完成后再注册的 MCP 工具或业务工具，Action 节点可见的 schema 仍为旧版本，出现「选型与执行不一致」的契约错位。

### 3.5 High — PlanExecuteStrategy 为空实现仍注册到工厂（暂不处理，CR之后会实现）

- **问题类型**：设计 / Bug
- **涉及文件**：`plan_execute/plan_execute_strategy.py`、`strategy_factory.py`
- **问题详情**：
  `PlanExecuteStrategy` 的 `build` / `as_node` / `as_subgraph` 方法全部为空实现（`pass`），但 StrategyFactory 仍按 ReAct 风格的参数构造该对象。调用方使用时极易触发 `TypeError` 或拿到无效的 `None` 返回值，且无任何告警。

### 3.6 Medium — retry_count 计数语义混用

- **问题类型**：设计缺陷
- **涉及文件**：`strategy/react/node/`
- **问题详情**：
  `retry_count` 同时统计「无工具可调用 / 工具名非法」的输入错误与「工具执行失败」的运行时错误，两种场景重试策略与根因不同，混用会导致错误场景过度重试或真实失败重试不足。

### 3.7 Medium — 无工具场景 prompt 与 schema 约定不一致

- **问题类型**：逻辑缺陷
- **涉及文件**：`strategy/react/node/reason_node.py`
- **问题详情**：
  Reason 阶段的提示词与结构化输出 schema 对「无需工具即可完成」的表述不一致，易触发模型空转输出无效格式，无谓消耗重试次数与 token。

### 3.8 Low — 枚举文件名拼写错误——已修改

- **问题类型**：代码规范
- **涉及文件**：`strategy/react/emums.py`
- **问题详情**：
  枚举文件名为 `emums.py`，存在拼写错误（应为 `enums.py`）。

## 四、graph 模块

### 4.1 Medium — 异步注册不完整，标记错误直接失败——已修复

- **问题类型**：逻辑 / 设计缺陷
- **涉及文件**：`graph/graph.py`、`graph/node/node.py`
- **问题详情**：
  `is_async` 标记仅注册 `run` 或 `arun` 其中一个实现，若标记与实际实现不匹配，调用会直接硬失败，缺少兼容降级与校验提示。
- **解决方案**：
  - `Graph.build` 使用 `RunnableCallable(node.run, node.arun)` 同时注册同步与异步路径
  - 移除 `Node.is_async`；纯同步节点的 `arun` 委托 `run`，保证 `ainvoke` 可达

### 4.2 Medium — 编译依赖运行时配置，职责倒置

- **问题类型**：架构设计
- **涉及文件**：`graph/root_graph.py`
- **问题详情**：
  `RootGraph.compile` 直接依赖 `RuntimeConfig`，图结构定义层反向依赖运行时层，模块职责倒置，不利于图结构的独立测试与复用。

### 4.3 Medium — 子图转节点方法重复且重复编译

- **问题类型**：设计缺陷
- **涉及文件**：`graph/subgraph.py`
- **问题详情**：
  `SubGraph.as_node` 与 `as_callable` 实现逻辑完全一致，且每次调用都会触发重新编译，存在冗余性能损耗与行为不一致风险。

### 4.4 Medium — 重名静默覆盖，无边拓扑校验

- **问题类型**：逻辑缺陷
- **涉及文件**：`graph/`
- **问题详情**：
  注册同名节点或子图时静默覆盖旧定义，无冲突告警；边注册时不做拓扑校验，可能出现无效边、循环依赖等运行时才暴露的问题。

### 4.5 Low — 抽象类无抽象方法，常量映射为死代码

- **问题类型**：代码规范
- **涉及文件**：`graph/graph.py`
- **问题详情**：
  `Graph` 标记为抽象基类（ABC）但未定义任何抽象方法；START/END 重映射逻辑无调用方，属于死代码。

## 五、model 模块

### 5.1 Medium — 工具白名单语义模糊——已修复

- **问题类型**：逻辑 / 安全风险
- **涉及文件**：`model/`
- **问题详情**：
  格式非法的 `allowed_tools` 会被转为空列表 `[]`，语义为「禁止所有工具」；而「无限制」语义为 `None`。两者行为差异巨大且无明确校验提示，配置错误易导致非预期的权限收缩。
- **解决方案**：
  保留 None = 未配置 / 不限制；遇到非法类型时抛出警告，不要静默 []；合法空列表 [] 才是「禁止额外业务工具」。
- 📌关于skill工具发现可能还需进一步设计

### 5.2 Low — 数据结构一致性不足——已修复

- **问题类型**：代码规范
- **涉及文件**：`model/`
- **问题详情**：
  - `append_messages` 为不可变操作，`ConversationState.append` 为可变操作，接口语义不一致
  - 枚举类型混用 `str Enum` 与普通 Enum
  - 部分目录缺少 `__init__.py`，包结构不规范
- **解决方案**：
  - 定义`ConversationState.append`的原因为在某些场景下不希望出现非USER和ASSISTANT的消息，但从逻辑上看，使用`append_messages`同样可以解决问题，只需定义好update的数据内容即可
  - 枚举类型均使用Enum，不使用`str Enum`
  - model模块不使用`__init__.py`，避免导出过于混乱

## 七、runtime 模块

### 7.1 High — 会话压缩阈值粘连，触发后每轮重复压缩

- **问题类型**：逻辑 Bug
- **涉及文件**：`runtime/algorithm/conversation_orchestrator.py` L61–88
- **问题详情**：
  压缩门控判断依赖 `token_usage.total_tokens`，但压缩操作仅修改 messages 与 summary 内容，**不回写更新 token_usage 数值**。首次触发压缩阈值后，判断条件长期为真，后续每轮对话都会重复执行一次 LLM 结构化压缩，造成不必要的耗时与 token 消耗。

### 7.2 Medium — 中断处理器定义缺失，双协议并存

- **问题类型**：Bug / 职责重叠
- **涉及文件**：`runtime/`
- **问题详情**：
  `InterruptHandler` 在 `__all__` 中导出但未实际定义；同时存在 interrupt schema 与 HITL 两套中断处理协议，职责重叠且逻辑不统一。

### 7.3 Medium — 状态裁定逻辑重复

- **问题类型**：职责重叠
- **涉及文件**：`runtime/`
- **问题详情**：
  HITL 流程与 Normalize 模块重复对会话状态进行裁定，逻辑冗余且易出现状态判定不一致。

### 7.4 Low — 抽象与实现冗余

- **问题类型**：设计债务
- **涉及文件**：`runtime/`
- **问题详情**：

  - `RuntimeContext` 对外导出但无实际消费者
  - HITL 同步实现嵌入异步 ReAct 流程中，架构不匹配
  - 同步与异步压缩实现近乎重复，代码冗余

### 7.5 High — 运行时上下文载体分裂，RunnableConfig 未有效承载配置

- **问题类型**：架构设计 / 集成可用性（使用与集成中发现）
- **涉及文件**：`runtime/runtime_config.py`、`runtime/runtime_context.py`、`graph/schema.py`（`BaseContext`）、`agent/agent.py`（`_build_runnable_config` / `_build_context`）、`agent/runnable_metadata.py`
- **问题详情**：
  当前运行时相关能力分散在多层，名实与可达性不一致，集成方难以在图执行期「快速拿到」完整配置目录：


| 载体                        | 实际内容                                                              | 问题                                                    |
| ----------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------- |
| `RuntimeConfig`             | 仅`checkpointer` / `store`                                            | 编译期基础设施，不含业务配置                            |
| `RuntimeContext`            | `thread_id` / `session_id` / `metadata`                               | 对外导出但无消费者，形同死抽象                          |
| `RunnableConfig`            | 仅`thread_id` + `configurable.metadata`（现主要是 `http_headers`）    | LangGraph 标准通道几乎空转                              |
| `BaseContext`（`context=`） | `agent_state`、`skill_list`、`active_skills`、`kb_list` 占位、`trace` | 真正的运行时上下文，但`kb_list` 未灌入、无 MCP 目录摘要 |
| `Agent` 实例字段            | 完整`AgentConfig`、`MCPClient`、`ToolRegistry` 等                     | 门面持有；节点若不经闭包则够不到                        |

集成诉求（将 `agent_config` / `skill_list` / `kb_list` / `mcp_list` 等放入可运行时读取的位置）方向正确，但不宜无差别全部塞进 `RunnableConfig.configurable`：含密钥的完整 `AgentConfig`（尤其 `llm_config.api_key`）、stdio 启动命令等进入 configurable 后易随 checkpoint / 日志 / 序列化泄漏。

- **建议切分（设计方向，非已实现）**：

  1. **目录类只读数据**（`skill_list`、`kb_list`、已注册 MCP 服务 / 工具名摘要、策略参数）→ 扩展并统一到 `BaseContext`（或复活真正被消费的 RuntimeContext 并与之合并）
  2. **请求 / 会话级键**（`thread_id`、租户、`agent_id`、非敏感 agent 名、出站 `http_headers`）→ `RunnableConfig.configurable`
  3. **编译基础设施**（checkpointer / store）→ 保持 `RuntimeConfig`（或显式改名为 GraphCompileOptions），与业务运行时上下文解耦

## 八、capability 模块

### 8.1 High — HTTP Skill 全部候选失败触发变量未定义错误

- **问题类型**：功能 Bug
- **涉及文件**：`capability/skill/skill_parser.py` L72–81
- **问题详情**：
  循环解析所有候选 Skill 全部失败时，`content` / `name` 变量未被赋值，后续仍调用 `_parse_frontmatter(content)` 触发 `UnboundLocalError`。现有测试仅断言「抛出任意异常」，掩盖了真实的失败形态。

### 8.2 High — HTTP Skill 包模型残缺，远程目录结构不可感知

- **问题类型**：功能缺失 / 逻辑缺陷（使用与集成中发现）
- **涉及文件**：`capability/skill/skill_parser.py`（`_parse_http`）、`capability/skill/skill_loader.py`、`tool/toolkit/skill.py`（`read_skill_resource` / `_aread_package_resource`）、`model/skill.py`（`SkillPackage`）
- **问题详情**：
  Remote（HTTP）Skill 在集成中实质不可用。配置 URL 仅作为 **base URL**：解析阶段只尝试拼接 `SKILL.md` 等候选文件名并拉取 frontmatter，**不会**像本地 FILE Skill 那样枚举 `scripts/`、`references/`、`assets/` 及附加资源。

因此形成与 FILE 不对等的能力缺口：


| 能力                               | FILE               | HTTP                                    |
| ------------------------------------ | -------------------- | ----------------------------------------- |
| 拉取`SKILL.md` + frontmatter       | 有                 | 有（仅候选文件名）                      |
| 枚举包内资源路径                   | 有（`_get_files`） | 无（字段恒为空列表）                    |
| `load_skill` 向模型告知可用资源    | 有                 | 无（通常仅返回「loaded」）              |
| `read_skill_resource` 读取包内文件 | 有                 | 无（非 FILE 直接`NotImplementedError`） |

根因是建模不一致：HTTP 被当作「单文件指令源」，FILE 才是「可列举的包」。远端没有本地 `rglob`，又缺少清单协议（frontmatter / manifest 声明相对路径）或按相对路径 `join_url(base, path)` 拉取并缓存的实现，模型既无法感知远端文件夹结构，也无法读取资源。即使修复 §8.1 的失败形态，在补齐包模型与资源读取之前，HTTP Skill 仍无法作为一等公民使用。

- **建议方向**：清单驱动（frontmatter 或旁路 manifest 声明资源相对路径）+ HTTP 路径下 `join_url` GET；补齐后再强化 §8.5 的 SSRF / 体积 / 超时约束。

### 8.3 Medium — 激活标识与配置键不一致导致静默失效

- **问题类型**：逻辑缺陷
- **涉及文件**：`capability/`
- **问题详情**：
  `active_skills` 以 frontmatter 中的 name 字段为标识，而外部 API 以 `skill_list` 的 key 为标识，两者不一致时 Skill 会静默处于 idle 状态，调用方无法感知失效。

### 8.4 Medium — 启动时全量解析，单点故障拖垮整体

- **问题类型**：设计缺陷
- **涉及文件**：`capability/`
- **问题详情**：
  Agent 构造时立即解析全部 Skill（含远程 HTTP Skill），单个远程 URL 加载失败就会导致整个 Agent 初始化失败，缺少降级与容错机制。

### 8.5 Medium — 远程 Skill 缺少安全约束

- **问题类型**：安全风险
- **涉及文件**：`capability/`
- **问题详情**：
  远程 HTTP Skill 未配置 SSRF 防护、响应体积限制、超时控制等安全策略，存在内网探测、资源耗尽等风险。补齐 §8.2 的按路径远程读取后，该面将更尖锐。

- **涉及文件**：`trace/agent_trace.py`、`agent/agent.py`（`stream` / `astream` 的 `stream_mode`）、`adapter/events.py`、策略 state（如 ReAct 的 `reasoning` / `task_status` / `step_count`）

  1. **State 内有过程信息**（如 ReAct 的 `reasoning`、`task_status`、`step_count`、`trajectory`），但是图内状态，不是对外 UI 契约

- **建议方向**：单独定义面向 UI 的投影模型（例如 phase / step / headline / active_tools / loaded_skills），在关键节点边界经 `custom`/`updates` 流或明确的 `AgentEvent` 类型吐出；`AgentTrace` 若继续承担观测职责应真正写入，或改名避免误导。
- **进度（关联 §2.5）**：
  - `LLMResult.reasoning` + 共享 `split_ai_content` 已提供模型侧推理原文
  - Adapter：`map_stream_chunk` 在 messages 流出现带 reasoning block 的 `AIMessage` 时，自动先发 `AgentEvent(type="reasoning", data={"text": ...})`，再发 `message`
  - 依赖图内 LLM 输出进入 `stream_mode="messages"`；若某节点 invoke 不冒泡到该流，则仍看不到 reasoning 事件（后续可针对路径补强）

## 十一、mcp 模块

### 11.1 Critical — 保留名可绕过内置工具权限控制

- **问题类型**：安全 / 契约缺陷
- **涉及文件**：`mcp/mcp_client.py` L46–54；消费方 `strategy/react/node/action_node.py` L26、L53–61
- **问题详情**：
  MCPClient 将配置中的 `name` 字段原样写入工具元数据 `meta_data["mcp_server"]`；ActionNode 仅通过字符串匹配判断，对名为 `fetch` / `filesystem` 的服务永久授予 always-expose 权限，不校验是否为受信内置服务。
  外部配置或用户输入只要将服务命名为 `fetch` / `filesystem`，即可绕过「内置工具默认关闭」的安全设计，获得与受信内置工具同等的模型可见性。

### 11.2 High — 空白目录解析为进程工作目录

- **问题类型**：安全 / 逻辑缺陷
- **涉及文件**：`mcp/builtin_mcp.py` L85–94
- **问题详情**：
  目录规范化函数中，空白字符串路径经 `Path("").resolve()` 解析后会得到进程当前工作目录（CWD）。上游 `AgentConfig` 仅校验非空列表，`mcp_allowed_directories=[""]` 可正常通过校验，导致 filesystem 工具作用域意外扩大到整个工作目录树。

### 11.3 High — Windows 下 cmd /c 拼接路径存在命令注入

- **问题类型**：安全风险
- **涉及文件**：`mcp/builtin_mcp.py` L44–51
- **问题详情**：
  Windows 平台通过 `cmd /c` 拼接启动命令，目录参数直接追加到命令行后。若路径包含 `&`、`|` 等特殊字符，会被 `cmd` 解析为命令分隔符，当目录来源可控时可构成本地命令注入。

### 11.4 High — Stdio 启动无约束，等价进程启动器

- **问题类型**：安全 / 设计缺陷
- **涉及文件**：`mcp/schema.py` L20–35、L49–57
- **问题详情**：
  Stdio 配置仅校验 `command` 字段存在，无命令白名单、环境变量隔离、工作目录限制等安全策略，配置原样透传给适配器执行。任何接收外部 `mcp_servers` 配置的入口，都等同于开放了本地任意进程启动能力。

### 11.5 High — 无生命周期管理，资源泄漏风险

- **问题类型**：功能 / 设计缺陷
- **涉及文件**：`mcp/mcp_client.py`
- **问题详情**：
  Client 仅提供构造、拉取工具、注册工具能力，无 `close` / `shutdown` 等销毁接口。stdio 子进程、HTTP 连接无法随 Agent 销毁而回收，频繁创建销毁场景下会出现子进程泄漏与连接泄漏。

### 11.6 High — 重名服务配置行为分叉

- **问题类型**：逻辑 Bug
- **涉及文件**：`mcp/mcp_client.py` L14–19、L41–43
- **问题详情**：
  构造阶段使用字典存储服务，重名配置后写入会覆盖前者；但注册工具阶段仍按原始完整列表逐个拉取注册。重复名称配置会出现静默错乱；默认空名称 `name=""` 会将所有未命名服务压缩到同一个 key 下。

### 11.7 Medium — 工具注册非原子，失败残留脏数据

- **问题类型**：逻辑缺陷
- **涉及文件**：`mcp/mcp_client.py` L37–60
- **问题详情**：
  注册过程为循环逐个拉取并注册，中途某服务失败时，前面已注册的工具不会回滚，残留到全局注册表中；重试时还会出现新旧工具集混杂的问题。

### 11.8 Medium — 服务名默认可空，身份体系脆弱

- **问题类型**：逻辑缺陷
- **涉及文件**：`mcp/schema.py` L20–21、L49–57
- **问题详情**：
  服务 `name` 字段默认可为空，空名称会破坏工具前缀约定、污染原始名称字段、加剧字典碰撞风险，整个服务身份体系几乎无校验。

### 11.9 Medium — args 可为 None 透传下游

- **问题类型**：逻辑 Bug
- **涉及文件**：`mcp/schema.py` L30–35
- **问题详情**：

### 11.10 Medium — 配置加载器为死代码且解析不完整
